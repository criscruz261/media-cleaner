# Live scanning and recovery

The Scanner page shows discovery activity, saved file progress and percentage, processed/total media bytes, remaining files, errors, and the latest checkpoint time. Active workers show current-file metadata/image work, bytes read during SHA-256, or video/animation sample progress. Discovery has no percentage because its final total is still unknown. Byte totals are logical media sizes, not an estimate of processing time.

Exact and similar groups appear with previews while other files are still processing. The page polls for live groups every second; scan snapshots also arrive through SSE, with polling fallback. Groups may gain members and their order may change. Live groups can be reviewed and cleaned during or after scanning: select unwanted files and use Delete selected per group. Confirmation, identity checks, fresh hashes, protected-file rules and a verified retained copy remain required. Cleanup serializes against match publication and file-result commits; afterward the worker rebuilds indexes from remaining ready files, preserving choices in a separate durable file-review table. New files start kept, and explicit choices take priority over automatic original-name suggestions. Exact original-name recommendations are finalized at completion. Approximate groups still start with every file kept.

The worker runs independently of the browser. Refreshing or reopening the local app restores the selected scan and saved form from browser storage and reconnects to its current status. If browser storage is unavailable or cleared, authenticated active-job discovery recovers the running job, or the latest paused/interrupted job. Reopening the page never creates or resumes a job automatically.

SQLite saves each completed file, identity, metadata, digest/descriptors, counters, and incremental results. After a backend restart, the scan is marked interrupted: choose **Resume**. Resume re-enumerates the roots and validates file identities, skips completed unchanged file work, and rebuilds provisional matching indexes from saved descriptors. Missing/changed files are reported rather than trusted. Explicit keep choices survive group rebuilds and restarts. Group IDs can change during rebuild, so an older cleanup preview may need to be recreated. New files discovered during resume are added to the totals.

Checkpoints are per completed file, not an open-directory cursor or partial SHA-256/decoder state. An unfinished file restarts safely; discovery and lightweight grouping may repeat. Current-file activity is transient. A decoder that was unavailable or skipped remains reported in warnings; install the needed tools and start a new scan to retry those comparisons. The app database remains in its local data directory; browser storage alone is not the checkpoint.

Graceful desktop server shutdown also pauses scans and waits for workers before closing the database. Reopen the app and choose **Resume**. Android saves the selected album and scan settings before discovery starts, so shutting down during discovery preserves the scope for **Continue Scan**. Completed files remain saved; unfinished files restart.

Desktop thumbnails and previews from saved results remain viewable after a drive remount changes its device number, provided the file path, inode, size and modification/change timestamps still match. This viewing check does not update saved identities or relax cleanup verification. Reconnect an unavailable drive to view its media.

## Folder-local checkpoints

Each entered root stores completed-file analysis in `.media-cleaner-cache/<key prefix>/<identity key>.json`. Files are written atomically after processing; explicit review choices update the corresponding entries. Multiple entered roots each keep their own file entries; overlapping roots use the deepest selected root. The cache is always excluded from discovery, including hidden-file scans, and is ignored by Git.

Entries contain SHA-256 when available, metadata, versioned fingerprints and explicit keep choices. A later scan of the same unchanged paths can reuse them, even with a fresh central app database. This rebuilds results in a new scan; it does not reconstruct the old job ID, scan history, cleanup plans or quarantine recovery history. Resume of an existing job still uses the central database. File identity and descriptor versions must match; corrupt or incompatible entries are ignored. Moving the collection or changing media causes reprocessing.

Media files are not changed. If a root is read-only, full, or its cache path is unsafe, scanning still saves to the central database and reports a warning. You can delete `.media-cleaner-cache` to discard this optional local copy; future scans will recreate it. This folder is an analysis cache, not a media backup or a replacement for the app's cleanup recovery records.
